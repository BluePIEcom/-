# 踩坑记录：为什么最后做成了"工具"，而不是"注入"

这份文档是这个项目最值钱的部分。它记录了我们从"注入摘要"改到"按需查询工具"的全过程，
以及每一步失败的原因——如果你要做类似的跨会话/跨插件同步，能省掉几个晚上的运气。

---

## 1. 需求长什么样

两个插件各自跑一个 DSH 会话：

- A：定时唤醒，读网页、写日记；
- B：实时聊天，挂长轮询等消息。

需求：**B 要知道 A 最近干了什么**，同时不能让 A 那边的第三方内容污染 B。

第一版方案很自然：在 B 每次收到消息时，把 A 的摘要拼进提示词。

---

## 2. 第一次失败：改错了投递路径

在 B 的代码里找到了构建提示词的函数 `buildWakePrompt(...)`，加了一段摘要注入，重启，测试。

**结果：日志里没有新增任何一行**，B 依旧说"我看不到"。

排查发现消息到达 B 有三条完全不同的路径：

| 路径 | 触发条件 | 构建函数 |
|---|---|---|
| 定时唤醒 | 定时器到点 | `buildWakePrompt` |
| 实时投递 | 会话空闲、来消息 | `deliverPromptNow` |
| **长轮询返回** | **agent 正挂着等消息的工具** | **不构造提示词，消息直接作为工具返回值** |

我们改的是第一条，而测试时走的是第二条。

---

## 3. 第二次失败：补了第二条，还是不行

把摘要注入复制到 `deliverPromptNow`，重启，测试——**日志还是没有**。

这时才注意到日志里一行关键信息：

```
会话繁忙，暂存唤醒原因（原因=turn）
```

以及紧跟其后的：

```
工具统一发送 …: 成功 1/1 条
```

意思是：**B 一直在长轮询（等待消息的工具调用）里**。消息在它等待期间到达，
直接被当成工具返回值交给模型，**整个过程没有重新构建过提示词**。

只要 agent 处于长轮询，任何"往提示词里加东西"的方案都不会执行——代码写得再对也没用。

---

## 4. 第三次失败：找到第三条路径，仍然不是根本解

我们在第三个投递入口（实时消息处理函数）也加了注入。这次理论上覆盖了所有路径。

但它依然是**错的方向**，因为：

1. 投递路径属于宿主/插件的内部实现，**会随版本变化**（三条路径已经改过两次命名）；
2. 每条路径都要维护一份注入逻辑，重复代码 = 迟早漂移；
3. 注入了也没法保证模型真的去用——它是"背景噪音"，不是"可执行的动作"。

---

## 5. 最终方案：把它做成工具

改成两步，简单得多：

1. 提供一个**可调用的工具** `digest_read(id)`，它去读对方导出的摘要；
2. 在人设/角色卡里写清楚：**什么时候该调用它**，以及为什么必须主动调。

结果第一次就通了。原因很朴素：

- 工具调用是**确定会执行**的路径，不管当前是长轮询、实时投递还是定时唤醒；
- 调用时机由模型决定，**问题一出现就能触发**，不需要等它"恰好经过某条投递路径"；
- 只在真的需要时花 token（拉模式），不会每轮都塞一段背景。

**结论：跨会话/跨插件共享，用"拉"（工具），不要用"推"（注入提示词）。**

## 6. 第二个教训：信任不能靠调用方声明

最初的记忆接口长这样：

```js
memory_append({ text, source: 'owner' })   // ← 灾难
```

看起来灵活，实际等于把升权按钮交给了调用方：一条被诱导的消息只要带上
`source: 'owner'` 就成了"使用者说的"，后面所有 agent 都会把它当指令执行。
而这正是提示注入最典型的路径：**第三方内容 → 摘要 → 另一个 agent 的上下文 → 执行**。

改成"信任钉在文件上"之后：

- 写进 `inbox` 的内容，**永远**按 `untrusted` 渲染，不管写的人怎么自称；
- `untrusted` 的追加会被**逐行引用化**（`> ` 前缀）并加固定横幅，伪造标题升不成规则；
- `trusted` 的 channel（人维护的事实文件）**根本不开放写工具**，agent 物理上写不进去。

---

## 7. 第三个教训：写权限要拆成"多个工具"

如果只有一个 `memory_append(channel, text)`，插件侧的工具守卫只能按**工具名**放行，
看不到参数，于是它无法表达"允许写 inbox、禁止写 self"。

拆成 `memory_append_inbox` / `memory_append_self` 之后，隔离变成结构性的：

```js
const SAFE_EXACT = new Set(['memory_read', 'digest_list', 'digest_read', 'memory_append_inbox'])
// 刻意不放 memory_append_self —— 它就不该能冒充"自己写的"
```

---

## 8. 第四个教训：安装脚本只动自己的块

给 `cordis.patch.yml` 加配置时，最直觉的做法是"用 YAML 库读进来 → 改 → dump 回去"。
但 DSH 的 patch 文件里有 `!!js` 标签、锚点、用户手写注释——**一次 dump 全部丢失或重排**，
用户下次打开文件会发现自己写的东西没了。

最后采用的是**注释标记区块**：

```yaml
# === dsh-shared-memory BEGIN ===
- insert:
    - id: mcp-shared-memory
      ...
# === dsh-shared-memory END ===
```

只替换这两个标记之间的内容，块外一个字节都不碰；首次写入前还会留一份带时间戳的备份。

---

## 9. 如果你要复用这些结论

| 场景 | 建议 |
|---|---|
| 两个 agent 想互相知道对方在干什么 | 提供 `digest_read` 类工具 + 人设里写清触发时机 |
| 第三方内容要进 agent 上下文 | 独立 `untrusted` channel + 强制引用化 + 固定横幅 |
| 想限制某个 agent 能写什么 | 按 channel 拆成多个工具，让守卫按工具名放行 |
| 要往宿主的配置文件里加东西 | 用注释标记区块，别整份 YAML 回写 |
| 不确定某段注入代码有没有执行 | **先加日志再改逻辑**；日志是唯一可信的观测 |
